A shopper pays once, but gets three order confirmation emails. Why? The payment provider delivered the same webhook three times. A timeout or lost response can trigger retries even after your server saved the payment. Webhooks are usually at least once, not exactly once. Here is the safe design. First, verify the signature using the raw request body. Next, insert the provider event ID into a PostgreSQL inbox with a unique constraint. In that same transaction, update the payment only if its state allows the transition, and write an outbox event. If the event ID already exists, acknowledge it without repeating the work. After commit, an asynchronous worker sends the email or fulfillment command using its own idempotency key. If that worker crashes, the outbox lets it retry. Watch duplicate delivery rate, outbox lag, and payment state mismatches. The lesson: one webhook can arrive many times, but the business action must be safe to repeat.
