⚠ Data exposure: this unsafe path returned another customer's order. A valid token did not make the request authorized.

Why this matters

OAuth 2.0 scopes control the type of operation. They do not automatically prove ownership of the requested object. A server must authorize every object lookup using verified identity and tenant context.

401 → invalid or missing authentication
403 → authenticated, missing permission
404 → absent or unowned order (demo policy)
200 → token, scope, and ownership all pass

A 404 concealment policy is a deliberate API design choice, not a universal rule.

Three practice challenges

Beginner — Identify the missing authorization step

A valid Alice token requests Bob's order. Under this demo policy, the result is 404 after a tenant-and-owner-scoped lookup returns no rows.

Intermediate — Build a secure order-history endpoint

Use `tenant_id` and authenticated `sub` in the WHERE clause, add stable keyset pagination, and test cross-tenant identity collisions.

Advanced — Temporary support-agent access

Require a narrowly scoped, time-limited approval for a specific order and purpose. Audit every access and deny requests after expiry or revocation.
